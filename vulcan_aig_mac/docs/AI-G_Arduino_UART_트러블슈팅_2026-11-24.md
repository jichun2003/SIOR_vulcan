# AI-G ↔ Arduino UART 연동 트러블슈팅 (2026-11-24)

> **상태: 미해결.** 보드 TX 출력은 확인됨. 우노 D2 수신이 안 되는 원인을 좁히는 중.

---

## 1. 개요

### 목표
- AI-G 보드에서 표적 추적 결과를 계산하고, 시리얼 명령으로 우노에 보내 포탑 서보를 구동함.
- 보드에 우노를 꽂을 USB-A 포트가 없음 → **보드 UART TX를 우노 RX에 직접 배선**하는 방식으로 진행.

### 구성
| 구분 | 내용 |
|---|---|
| 보드 | Telechips AI-G (`topst@aig-board`), 노트북과 랜선으로 ssh 접속 (`10.42.0.x`) |
| 노트북 | Ubuntu (`hoyong-tuf`) — ssh, 우노 업로드, picocom 모니터링 |
| MCU | Arduino Uno **CH340 호환보드** (노트북에서 `/dev/ttyUSB0`) |
| 펌웨어 | `model_control.ino` — 9600bps, 명령 `s2/s3 <deg>`, `c`, `t<ms>`, `f`, `x`, `v<0-255>` |
| 액추에이터 | Pan 서보 D3, Tilt 서보 D9, 모터 D5 / 서보 전원은 7.4V LiPo 별도, GND만 공통 |
| 보드 코드 | `~/vulcan_aig_bundle_1124_2/run.sh` (standalone 모드) → `uart.c`가 `--port`로 지정한 포트에 송신 |

### 전제 (이미 확인된 것)
- 우노 + 서보 + 펌웨어는 **윈도우 노트북에서 USB로 명령을 보냈을 때 정상 동작**함.
- 보드 코드는 수정할 필요가 없음.
  - 송신 형식(9600, 8N1, `s2`/`s3` 30ms 주기, 사격 `v`/`t`, 정지 `x`)이 `model_control.ino`와 동일함.
  - `run.sh`에서 `--port`만 실제 UART 장치로 바꾸면 됨.
- 통신은 **보드 → 우노 단방향**으로 충분함.
  - 피드백은 카메라 영상이 담당함(시각 피드백). 서보는 실제 각도를 출력하지 않으므로 우노에서 각도를 되받을 필요가 없음.
- 코드상 미구현 사항(동작에는 지장 없음)
  - 사격은 보드 터미널에 `shot`을 입력해야만 가능함.
  - 우노의 응답(`Fire done` 등)은 읽지 않음.

## 2. 진행 경과

### 1단계 — 40핀 헤더 UART (`/dev/ttyAMA1`)
- **가정:** 40핀이 라즈베리파이 배치를 따른다고 보고 8번 = TX, 10번 = RX, 6번 = GND로 사용함.

| 테스트 | 목적 | 결과 | 해석 |
|---|---|---|---|
| 8번 → D0 연결 후 `s2 60/120` 반복 송신 | 포탑 구동 확인 | 움직이지 않음 | — |
| 배선 재확인 | 연결 오류 확인 | 8번 → D1, 10번 → D0으로 **TX/RX가 반대로** 꽂혀 있었음 | 교정 후에도 안 됨 |
| `ls -l /dev/ttyAMA*`, `dmesg` | 장치 확인 | `ttyAMA1`(0x18010000), `ttyAMA2`(0x18020000, `console=ttyAMA2,115200`) | ttyAMA2는 커널 콘솔이므로 ttyAMA1을 후보로 선택 |
| `/proc/tty/driver/ttyAMA` | 드라이버 송신 여부 | ttyAMA1 `tx` 카운터 증가 | 소프트웨어상 송신은 정상 |
| **8·10번 루프백** (`HELLO`) | 핀으로 신호가 실제로 나가는지 | tx 17279 → 17284(+5), **rx 26879 변화 없음**, 수신 데이터 없음 | 신호가 핀으로 물리적으로 나오지 않음 |
| 멀티미터 (GND = 6번) | 핀 전압 확인 | 17번(3.3V) = 3.3V(측정기 정상), 10번 대기 = 2.6V, 송신 중 뚜렷한 변화 없음 | — |

- 측정 도중 리드가 옆 핀에 닿아 **보드가 리셋됨** → IP가 바뀜(.153 → .155 → .156). `nmap`으로 다시 찾아서 접속함.
- 참고: rx 카운터의 `26879 fe:81 brk:69`는 10번이 D0에 물려 있던 동안 들어온 값으로 추정됨.
- **결론:** ttyAMA1은 드라이버상 송신은 되지만 40핀 8·10번으로 신호가 나오지 않음. 핀 설정(디바이스트리/pinmux) 문제로 추정되나 **확인하지 않음.**

### 2단계 — 디버그 UART 헤더 (`/dev/ttyAMA2`)로 전환
- 부팅 로그 확인용으로 쓰던 4핀 헤더(`UART_5V / TX / RX / GND`)를 사용하기로 함.
- 이 포트는 콘솔이라 로그인 프롬프트와 커널 메시지가 우노로 섞여 들어감 → 아래 명령으로 일시 비활성화함.
  ```
  sudo systemctl stop serial-getty@ttyAMA2.service; sudo dmesg -n 1
  ```
  - **재부팅하면 다시 켜지므로** 부팅할 때마다 실행해야 함.
- ssh는 랜선으로 연결돼 있어서 USB-TTL을 빼도 끊기지 않음을 확인함.

### 3단계 — 디버그 TX → 우노 D0
| 테스트 | 결과 | 해석 |
|---|---|---|
| 우노 USB를 노트북에 연결하고 picocom으로 관찰, `zz` 입력 | `got: zz`라는 응답이 옴 | **우노에 `model_control.ino`가 아닌 echo 테스트 코드가 올라가 있었음** → 이전까지 서보가 안 움직인 이유 중 하나 |
| 보드에서 `hello` 송신 | `got: ` (빈 줄)만 출력됨 | 무언가 들어오지만 글자가 깨짐 |
| 우노 D0 전압 측정 | 0.5V | **우노 뒷면에서 측정함 → 핀이 좌우로 뒤집혀 보여서 다른 핀을 쟀을 가능성이 큼. 신뢰도 낮음** |
| `lsusb` | `1a86:7523 CH340` | 호환보드임을 확인함 |

- **조치:** D0은 USB 변환칩(CH340)과 공유되는 핀이라 충돌 가능성이 있다고 판단함 → **SoftwareSerial로 D2를 RX로 쓰도록 펌웨어를 수정함.**
  - 송신 핀은 D4로 지정했으나 연결하지 않음.
  - 서보(D3, D9)와 모터(D5) 핀은 그대로 둠.
  - 노트북 USB 명령도 그대로 받음.
  - USB와 D2가 분리되므로 picocom으로 관찰하면서 시험할 수 있게 됨.

### 4단계 — 우분투에서 펌웨어 업로드 (arduino-cli)
- 노트북에 `model_control.ino`가 없어서 파일을 받아 `~/model_control/`에 배치함.
- 업로드 명령:
  ```
  export PATH=$PATH:$HOME/.local/bin
  arduino-cli compile --fqbn arduino:avr:uno ~/model_control && arduino-cli upload -p /dev/ttyUSB0 --fqbn arduino:avr:uno ~/model_control
  ```
- 업로드 중 `not in sync` 에러가 한 번 발생함(D0에 보드 TX가 연결된 상태였을 가능성 있음).
- 새 코드가 올라갔는지 구분하려고, 시작할 때 **`[link] AI-G cmd input = D2 (9600)`**를 출력하도록 펌웨어에 추가함.
- 재업로드 후 picocom에서 **`[link]` 배너가 출력되는 것을 확인함** → D2 수신 펌웨어가 정상적으로 올라감.
- picocom이 포트를 잡고 있으면 업로드나 재접속이 실패함(`cannot lock /dev/ttyUSB0`) → `sudo pkill picocom`으로 해결함.

### 5단계 — 보드 TX 핀 확정, TX → D2 시험
**TX 핀 확정** (점퍼선을 빼고 디버그 헤더 GND 기준으로 측정)

| 핀 | 대기 전압 | 송신 중 (`yes U` 연속 송신) | 판정 |
|---|---|---|---|
| `RX` 표시 핀 | (3.3V, 풀업) | 변화 없음 | 입력 핀 |
| **`TX` 표시 핀** | **4.8V** | **2.6V로 하락** | **보드 TX 확정** |

- 디버그 헤더는 **5V 레벨로 출력됨**(보드에 레벨 변환 회로가 있는 것으로 추정). → 우노(5V)에 **레벨시프터 없이 직결해도 됨.**
- 9600bps 신호가 핀에서 실제로 나오는 것을 확인함.

**TX → D2 시험**

| 테스트 | 결과 |
|---|---|
| `TX` 핀 → D2, 포트를 열어둔 채(`exec 3<>`) 9600 고정 후 `zz` 반복 송신 | `Unknown command: zz`가 출력되지 않음 |
| USB-TTL 어댑터 TX → D2로 `zz` 송신 | 응답 없음. 단, **어댑터 자체의 정상 여부를 확인하지 않아서 신뢰도 낮음** |
| **바이트 덤프 펌웨어** 업로드 (D2로 들어온 바이트를 `[d2 7A]` 형식으로 출력) | 우노 헤더에 직접 꽂았는데도 **`[d2 ...]`가 하나도 출력되지 않음** |

- **해석:** 깨진 바이트조차 없음 → D2에서 신호 변화를 전혀 감지하지 못하고 있음.

### 6단계 — 우노 쪽 D2 전압 측정 (미완료)
- 보드에서 10초 연속 송신 중 **우노 GND ↔ 우노 D2** 전압을 재는 단계까지 진행함. **결과를 확인하기 전에 작업을 중단함.**

## 3. 확인된 사실
1. 보드 소프트웨어(`uart.c`, 9600 8N1, 명령 형식)는 우노 펌웨어와 호환되며 수정할 필요가 없음.
2. 40핀 8·10번(ttyAMA1)은 현재 설정에서 핀으로 신호가 나오지 않음(루프백 rx 0).
3. **디버그 헤더 `TX` 표시 핀 = 보드 TX(ttyAMA2), 5V 레벨, 9600 신호 출력 정상.**
4. 우노는 CH340 호환보드이며, 작업 초반에는 echo 테스트 코드가 올라가 있었음.
5. TX → D2로 연결했을 때 우노에서 수신 바이트가 0개임.
6. 따라서 문제 구간은 **보드 TX 핀 → 우노가 D2를 읽는 부분 사이**로 좁혀짐.

## 4. 정정 사항 (작업 중 잘못 판단했던 것)
- **레벨시프터·다이오드:** 3.3V 출력을 전제로 레벨시프터가 필요하다고 판단했으나, 디버그 헤더는 5V 출력이라 해당하지 않음. 다이오드 방식은 우노 D0이 5V로 풀업돼 있어서 애초에 보호가 되지 않는 방법이었음.
- **D0 0.5V → "CH340이 D0을 붙잡음" 판단:** 뒷면 측정이라 다른 핀을 쟀을 가능성이 있음. 근거가 약함. D2로 옮긴 조치 자체는 유효함.
- **TX/RX 표시 혼동:** 한때 `RX` 표시 핀이 실제 TX일 수 있다고 의심했으나, 측정 결과 `TX` 표시가 맞았음.
- **"정품 우노는 1kΩ, 호환보드는 약함":** 추정이며 확인되지 않음.

## 5. 미해결 — 원인 후보
1. ~~펌웨어 미반영~~ → `[link]` 배너를 확인했으므로 **가능성 낮음**. 단, 바이트 덤프 버전(`DEBUG_LINK`)을 올린 뒤 업로드 성공 여부를 별도로 확인한 기록은 없음.
2. **GND 공통 불량:** 보드 디버그 GND와 우노 GND가 실제로 연결돼 있지 않을 가능성.
3. **배선·접촉 불량:** 점퍼선 단선이거나, 우노 쪽에서 D2가 아닌 핀에 꽂혔을 가능성.
4. (참고) 40핀 UART 미출력의 원인(디바이스트리/pinmux)은 조사하지 않음.

## 7. 연결·실행 순서 (노트북 ↔ AI-G ↔ 우노)

### 기본 원칙
- 디버그 헤더 하나를 **처음에는 USB-TTL(콘솔용)**, **나중에는 우노(명령 송신용)**가 번갈아 씀 → 둘을 동시에 꽂지 않음.
- 보드 접속은 랜선 ssh로 함. USB-TTL은 부팅 확인과 IP 확인용 보조 수단임.
- 전원은 **"보드 먼저 켜고, 우노 나중에 켜고, 끌 때는 우노 먼저"** 순서를 지킴.

### 켤 때
| 순서 | 작업 | 이유 |
|---|---|---|
| 1 | 노트북 ↔ 보드 **랜선** 연결, 디버그 헤더에 **USB-TTL** 연결 (우노는 아직 연결 안 함) | 노트북이 공유 네트워크(`10.42.0.x`)로 보드에 IP를 나눠줌. USB-TTL은 부팅 로그와 로그인 화면을 보기 위함 |
| 2 | 보드 전원 ON → 노트북에서 `sudo picocom -b 115200 /dev/ttyUSB0`로 부팅 확인 | 보드가 정상 부팅됐는지 확인함. 콘솔 속도는 115200 |
| 3 | **IP 확인**: 콘솔에서 `ip a`, 또는 노트북에서 `sudo nmap -sn 10.42.0.0/24` | 재부팅할 때마다 IP가 바뀜(.153 → .155 → .156) |
| 4 | 노트북에서 `ssh topst@10.42.0.<IP>` 접속 확인 | 이후 작업은 모두 ssh 창에서 함 |
| 5 | picocom 종료(Ctrl+A → Ctrl+X) 후 **USB-TTL 분리** | 디버그 헤더를 우노용으로 비워야 함. ssh는 랜선이라 USB-TTL을 빼도 끊기지 않음 |
| 6 | ssh 보드 창에서 **콘솔 끄기** `sudo systemctl stop serial-getty@ttyAMA2.service; sudo dmesg -n 1` | ttyAMA2는 콘솔 겸용이라 그대로 두면 로그인 프롬프트와 커널 메시지가 우노로 흘러감. 재부팅하면 되살아남 |
| 7 | 우노 전원이 꺼진 상태에서 배선: 디버그 `TX` → 우노 **D2**, 디버그 GND → 우노 GND | 전원이 들어간 상태에서 배선하면 오접촉 위험이 있음. GND가 없으면 신호 기준이 없어 수신이 안 됨 |
| 8 | **우노 전원 인가** — 노트북 USB 또는 보드 4번(5V) 중 **하나만** 사용 | 보드가 꺼진 상태에서 우노만 켜져 있으면 신호선과 전원으로 역전원이 들어감(우노를 연결한 채 보드 전원을 넣었을 때 부팅 실패 경험 있음). 전원을 두 곳에서 동시에 주면 충돌함 |
| 9 | (노트북 USB 전원이면) `sudo picocom -b 9600 /dev/ttyUSB0`로 `[link] AI-G cmd input = D2 (9600)` 배너 확인 | 올바른 펌웨어가 올라갔는지 확인함. picocom을 열면 우노가 리셋되므로 1~2초 기다림 |
| 10 | ssh 보드 창에서 송신 시험 → 서보 시험 → `bash run.sh` | 단계별로 통신, 구동, 전체 동작 순서로 확인함 |

- 우노 전원 선택
  - **노트북 USB:** 디버깅 단계에서 사용. picocom으로 우노가 받은 내용을 볼 수 있음.
  - **보드 4번(5V):** 실제 운용 시 사용. 노트북 없이 동작함.

### 이 순서를 지켜야 하는 이유 — 부팅 실패 사례
**실패한 순서**
1. 우노를 보드에 미리 연결해 둠: 40핀 4번(5V) → 우노 5V, TX → D0, GND 공통.
2. 그 상태에서 보드 전원을 넣음.
3. USB-TTL과 랜선으로 접속을 시도함.

- 우노 전원은 **보드 4번 핀에서만** 받음(별도 전원 없음). 보드가 꺼져 있으면 우노도 꺼져 있는 상태.

**증상**
- 디버그 콘솔(picocom)에서 Enter를 눌러도 `login:`이 나오지 않음 → 보드가 부팅을 못 한 상태. IP를 못 찾은 것이 아니라 **부팅 자체가 안 된 것**.
- `nmap`으로 IP가 잡히지 않음 → 랜 인터페이스도 올라오지 않음.
- 한때 노트북 쪽 USB-TTL 연결이 끊김(`read zero bytes from port`).
- 이후 디버깅 과정에서 우노를 **노트북 USB로 따로 전원**을 주고 4번 선을 뺀 상태로 다시 켰으나 여전히 부팅되지 않음.
- **40핀의 선과 우노 USB를 전부 빼고** 보드 전원을 다시 넣자 바로 정상 부팅됨(IP `10.42.0.155`).

**성공한 순서**
1. 보드를 단독으로 부팅함.
2. IP를 찾고 ssh로 접속을 확인함.
3. 그 뒤에 4번 핀에서 우노 전원과 신호선을 연결함 → 보드는 정상 동작을 유지함.

**원인 (추정)**

① 첫 실패 — 우노가 보드 4번 핀에서만 전원을 받을 때
- 보드가 꺼진 동안 우노도 꺼져 있었으므로 "꺼진 보드에 우노가 전기를 넣는" 상황은 아님.
- 문제는 **전원이 들어오는 순간의 순서(파워 시퀀싱)**로 추정됨.
  - 40핀 4번(5V)은 어댑터 입력에서 거의 바로 나오는 전원이라, 어댑터를 꽂자마자 우노가 먼저 켜짐.
  - 반면 SoC 내부 전원(코어·IO 3.3V 등)은 PMIC가 정해진 순서로 나중에 올림.
  - 그 사이 이미 켜진 우노가 신호선으로 **아직 전원이 안 올라온 SoC 핀에 전압을 걸게 됨**.
    - D1: 대기 상태 HIGH → 분배저항을 거쳐 보드 10번 핀으로 들어감.
    - D0: USB칩 쪽 5V 풀업 → 보드 8번 핀으로 들어감.
  - 이 전압이 칩 내부 보호 다이오드를 타고 IO 레일을 먼저 띄움 → PMIC의 전원 시퀀스와 파워온 리셋이 꼬여서 부팅이 멈춤.
- 보조 요인 (확인 안 됨)
  - 부팅 순간 우노와 쉴드가 4번 핀에서 끌어가는 돌입 전류 때문에 보드 5V가 순간적으로 떨어졌을 가능성.
  - 40핀 일부가 부트 모드 설정 핀(strap)이어서 외부 전압 때문에 부트 모드가 바뀌었을 가능성.
- **쉴드 서보 전원 역류는 원인이 아님:** 서보는 `servo_lipo`(7.4V), DC모터는 별도 LiPo를 쓰고, 우노 5V와 공유하는 것은 GND뿐임을 회로로 확인함.

② 이후 실패 — 우노를 노트북 USB로 따로 켰을 때
- 이때는 보드가 꺼져 있어도 우노는 켜져 있음 → 신호선을 통한 **역전원(back-powering)**이 계속됨.
- 보드 IO 레일이 반쯤 살아 있는 상태가 유지되어, 어댑터를 다시 꽂아도 전원이 0V부터 깨끗하게 올라오지 않음 → 리셋 실패.
- 선을 **전부** 빼서 보드를 완전히 방전시킨 뒤에야 정상 부팅됨 → 관찰 결과와 일치함.

- ①과 ②의 공통점: **보드 SoC 전원이 완전히 올라오기 전에 우노가 이미 살아서 신호선에 전압을 걸고 있었음.**
- 원인은 **100% 확정되지 않음.** 대책은 같음.

**보드 부팅 후에 연결하면 되는 이유**
- 부팅이 끝나면 SoC의 모든 전원 레일이 안정된 상태임 → 우노 신호선의 전압이 들어와도 정상 입력으로 처리되고, 역전원 경로가 생기지 않음.
- 파워 시퀀스, 리셋, 부트 모드 판정이 이미 끝난 뒤임 → 외부 신호가 부팅에 영향을 주지 않음.
- 우노가 4번 핀에서 끌어가는 전류도 이미 안정된 5V 레일에서 공급됨.

**결론 (규칙)**
- 보드 SoC가 완전히 부팅되기 전에는 우노가 **전원도 신호선도 살아 있으면 안 됨**.
  - 우노 전원이 보드 4번 핀이더라도 **미리 꽂아 둔 채로 보드를 켜지 않음**.
- **켤 때:** 보드 → (IP·ssh 확인) → 우노.
- **끌 때:** 우노 → 보드.
- 부팅이 꼬였을 때: 보드에 연결된 선을 **전부** 빼고 몇 초 기다린 뒤 보드만 단독으로 켬.

### 끌 때
1. 보드에서 실행 중인 프로그램을 종료함(Ctrl+C).
2. **우노 전원을 먼저 분리**함(4번 5V 선 또는 USB).
3. 보드를 종료함 → 보드 전원을 분리함.

### 재부팅했을 때
- IP를 다시 확인함(3번).
- 콘솔 끄기를 다시 실행함(6번).
- 우노가 4번 핀 전원이면 **재부팅 전에 먼저 분리**하고, 부팅이 끝난 뒤 다시 연결함.

## 9. 명령어 모음

**보드 접속**
```
sudo nmap -sn 10.42.0.0/24        # 보드 IP 찾기 (10.42.0.1이 아닌 주소)
ssh topst@10.42.0.<IP>
```

**보드: 콘솔 끄기 (부팅할 때마다)**
```
sudo systemctl stop serial-getty@ttyAMA2.service; sudo dmesg -n 1
```

**보드: 포트를 열어둔 채 반복 송신 (수신 시험용)**
```
sudo sh -c 'exec 3<>/dev/ttyAMA2; stty -F /dev/ttyAMA2 9600 raw -echo -crtscts clocal; while true; do echo zz >&3; sleep 0.5; done'
```

**보드: 서보 시험**
```
sudo sh -c 'exec 3<>/dev/ttyAMA2; stty -F /dev/ttyAMA2 9600 raw -echo -crtscts clocal; for i in 1 2 3; do echo "s2 60" >&3; sleep 1; echo "s2 120" >&3; sleep 1; done'
```

**보드: 전압 측정용 연속 송신 (10초)**
```
sudo sh -c 'exec 3<>/dev/ttyAMA2; stty -F /dev/ttyAMA2 9600 raw -echo; timeout 10 sh -c "yes U | tr -d \"\\n\" >&3"'
```

**보드: UART 송수신 카운터**
```
sudo cat /proc/tty/driver/ttyAMA
```

**노트북: 우노 모니터**
```
sudo picocom -b 9600 /dev/ttyUSB0      # 종료: Ctrl+A → Ctrl+X
sudo fuser -v /dev/ttyUSB0; sudo pkill picocom   # 포트 점유 해제
```

**보드: 최종 실행**
```
sed -i 's#/dev/ttyAMA1#/dev/ttyAMA2#' run.sh && bash run.sh
```

## 10. 주의사항
- **우노를 보드 4번 핀(5V)에서 전원 공급할 때**
  - 보드가 완전히 부팅된 뒤에 연결함.
  - 보드를 끄거나 재부팅하기 전에 먼저 분리함.
  - 우노를 연결한 상태로 보드 전원을 넣었을 때 보드가 부팅되지 않은 적이 있음(역전원으로 추정).
- **우노 USB와 4번 핀 5V를 동시에 연결하지 않음.**
- **업로드 전 확인 사항**
  - picocom을 닫음.
  - D0을 사용 중이면 D0 선을 뺌.
- picocom으로 포트를 열면 우노가 리셋됨 → 배너가 뜰 때까지 1~2초 기다린 뒤 송신함.
- 멀티미터로 측정할 때는 **앞면 헤더 기준**으로 잼. 뒷면은 핀 순서가 좌우로 뒤집혀 보임.
- 40핀 측정 중 리드가 옆 핀에 닿으면 보드가 리셋되고 IP가 바뀔 수 있음.

- 덤프 코드를 추가함: `char ch = link.read();` 다음 줄에 `[d2 XX]`를 출력하도록 함. 재업로드 후 배너가 정상 출력됨.

  - D2 SoftwareSerial 수신
  - 시작 배너
  - 바이트 덤프
- 참고: USB 명령은 `readStringUntil('\n')`의 1초 타임아웃 때문에 Enter 없이도 처리됨(정상 동작).

### 쉴드 정전기 사고
- 쉴드를 만지다가 사격용 MOSFET(IRLB8721) 부근에서 정전기가 발생함.
  - 이후 사격 모터가 스스로 돌기 시작해 점점 빨라짐.
  - 우노를 분리해도 멈추지 않았고, 사격 모터 배터리를 빼서 정지시킴.
- 게이트 풀다운 저항은 PCB에 원래 있었음.
  - → 정전기로 인한 **MOSFET 손상**(게이트 절연 파괴 → 반쯤 켜짐 → 발열 → 더 많이 켜짐)으로 추정함.
- PCB를 재납땜함.
- 이후 우노 리셋 시 터렛이 한 번 움직임 → 서보 초기 위치 이동으로 판단함(정상).

### 보드 부팅과 USB-TTL
- USB-TTL 없이 켰을 때는 nmap에 잡히지 않았음.
- USB-TTL의 **TX → 보드 RX, GND**를 연결하고 켜면 매번 잡힘(.153 / .155 / .154).
- **추정:** 보드 RX가 약하게만 풀업돼 있어서 잡음이 들어오고, 부트로더(U-Boot)가 이를 키 입력으로 인식해 자동 부팅을 멈춤.
- **규칙:** 보드를 켤 때는 USB-TTL TX → 보드 RX와 GND를 연결해 둠. 대안으로 RX ↔ 3.3V 사이에 10kΩ 풀업을 다는 방법도 있음(미검증).
- 보드가 켜져 있어도 나중에 USB-TTL을 꽂으면 회복되지 않음 → 반드시 전원을 껐다 켜야 함.
- USB-TTL을 빼고 우노를 배선하는 과정에서 보드가 한 번 멈춤. 어느 단계였는지는 확인하지 못함.
  - 이후 별도 터미널에서 `ping`을 계속 띄워 두고 단계마다 확인하는 방식으로 진행함.

### 디버그 헤더 TX 고장 확인
| 측정 (보드 GND 기준, DC V) | 11/24 | 11/25 |
|---|---|---|
| `TX` 대기 | 4.8V | **0.49V** |
| `TX` 송신 중 | 2.6V | **0.26V** |
| `RX` (단독) | 3.3V | 3.3V (USB-TTL TX 연결 시 4.9V) |
| `UART_5V` | (미측정) | 0V |

- 40핀 17번(3.3V)으로 멀티미터 정상 여부를 확인함.
- 선을 전부 빼도, 뒷면 납땜부에서 재도, **5분간 전원을 차단한 뒤 다시 켜도** 0.49V로 동일함 → 복구형 퓨즈 문제가 아니라 **출력부 손상**으로 판단함.
- USB-TTL의 VCC를 `UART_5V`에 연결해도 변화 없음.
- 오늘 USB-TTL 콘솔(picocom)이 아무것도 표시하지 않았던 것도 같은 원인으로 설명됨(보드 TX → USB-TTL RX 경로 불능).
- ssh는 랜선을 쓰므로 영향 없음.
- 손상 시점은 미확정. 보드가 꺼져 있거나 부팅 중일 때 우노 쪽 전압이 들어간 상황이 가장 의심됨.

### 우노 D2 수신 확인
- 보드 TX(LOW 고정)에 D2를 연결하는 순간 picocom에 `[d2 0]`이 출력됨 → D2가 HIGH → LOW 변화를 감지함.
- **우노 D2 수신, 펌웨어, 우노 쪽 배선은 정상.**

### 40핀 UART(ttyAMA1) 조사
- 보드 단독, 대기 상태 측정: **8번 = 0V**, **10번 = 2.6V** → 8번이 UART TX로 동작하지 않음(정상이면 3.3V).
- 사용 가능한 장치
  - UART: `ttyAMA1`, `ttyAMA2`
  - I2C: `i2c-0`, `i2c-1`, `i2c-3`
  - SPI: `spidev0.0`, `spidev3.0`
  - USB: **호스트 없음**(`/sys/bus/usb/devices` 비어 있음) → USB로 우노를 연결하는 방법은 불가
- 디바이스 트리(`dtc -I fs -O dts /proc/device-tree`)
  - `serial@18010000` (= serial1 = ttyAMA1): `status = "okay"`, `pinctrl-0 = <0x0f>`
  - `0x0f` = `uart1_data`: 핀 **`gpf-0`, `gpf-1`**, function 1
  - `gpf-0`/`gpf-1`을 쓰는 다른 항목은 없음(충돌 없음). GPIO로 점유되어 있지도 않음.
  - `config-reg = <0x180c0000 0x08 0x09>`는 세 UART에 모두 동일함 → 포트 선택 값이 아니라 공통 설정으로 보임.
  - 해당 레지스터를 `/dev/mem`으로 읽으려 하면 `Bus error`가 남 → 직접 읽기 불가.
- **미확정:** `gpf-0`/`gpf-1`이 실제로 40핀 몇 번에 연결돼 있는지.

### I2C로 전환 — 통신 성공
**버스 확인**
- `i2cdetect -l`: `i2c-0`(18100000), `i2c-1`(18110000), `i2c-3`(16070000)
  - `i2c-0`: 0x60/0x61/0x63이 `UU`(보드 내부 칩이 사용 중) → 사용하지 않음
  - `i2c-1`: 비어 있음 → **40핀 3번(SDA)·5번(SCL) = `i2c-1`**
  - `i2c-3`: 카메라 쪽으로 추정 → 건드리지 않음
- 40핀 3번·5번 대기 전압: 둘 다 3.3V(보드 풀업 있음)

**우노 확인용 스케치 `i2c_test.ino`**
- 슬레이브 주소 0x08, 받은 바이트를 USB로 출력함.
- `Wire.begin()` 후 `digitalWrite(SDA/SCL, LOW)`로 **내부 5V 풀업을 끔** → 보드 3.3V 핀 보호.

**배선**
- 40핀 3번 → 우노 A4
- 40핀 5번 → 우노 A5
- 40핀 9번 → 우노 GND

**결과**
- `sudo i2cdetect -y 1` → **`08` 검출**
- `sudo i2ctransfer -y 1 w3@0x08 0x7a 0x7a 0x0a` → `[i2c 7A] z`, `[i2c 7A] z`, `[i2c A]`
- `sudo i2ctransfer -y 1 w6@0x08 0x73 0x32 0x20 0x36 0x30 0x0a` → `s2 60\n` 6바이트 정상 수신
- **보드 → 우노 I2C 통신이 정상 동작함.**

**남은 작업**
- `model_control.ino`에 I2C 수신 추가(기존 명령 처리 재사용)
- 보드 송신 코드(`uart.c`)를 I2C로 보내도록 수정(`/dev/i2c-1`, 주소 0x08)

## 12. 2026-11-26 추가 — 추적 폭주 원인 해결

### 증상
- 표적을 잡고 따라가다가 포신이 갑자기 위로 치솟거나 아래로 꽂힘.
- 좌우는 정상이고, 위아래로 조금만 움직여도 그 방향 끝까지 가버림. 끝에 걸리면 "삐" 소리가 남.
- AI-G(I2C)뿐 아니라 **윈도우 + aaa_code_1111 + USB 시리얼**에서도 똑같이 발생함 → 소프트웨어가 원인이 아님.

### 원인 확인
- 로그(`--log-csv`)로 명령각을 확인함 → 명령은 프레임마다 조금씩 변하는데 서보는 끝까지 감.
- 시리얼 모니터에서 `s3 90` → `s3 70`을 보내니 20°만 움직이지 않고 **위로 끝까지 계속 돌다가** 걸려서 삐 소리가 남.
- **원인: tilt 서보가 360° 연속 회전 서보였음.**
  - 360° 서보는 명령값이 각도가 아니라 **속도와 방향**임(90 = 정지, 90에서 벗어나면 그 방향으로 계속 회전).
  - 위치를 스스로 유지하지 못하므로, 각도 명령을 쓰는 추적 코드에서는 위아래가 폭주함.
- **조치: tilt를 일반 180° 서보로 교체함** → 윈도우(1111)에서 정상 추적을 확인함.

### 참고
- 이 과정에서 확인함: `s3` 값을 줄이면 포신이 위로 올라감.
- 방향 부호는 기본값(+1)으로 윈도우에서 정상 동작함. 서보를 교체했으므로 AI-G에서 처음 실행할 때 다시 확인할 것.

## 13. 최종 실행 방법 (AI-G + I2C, 2026-11-26)

### 구성
| 항목 | 내용 |
|---|---|
| 보드 → 우노 통신 | **I2C** `/dev/i2c-1`, 우노 주소 0x08 |
| 배선 | 40핀 3번(SDA) → A4 / 40핀 5번(SCL) → A5 / 40핀 9번(GND) → GND |
| 우노 펌웨어 | `model_control_i2c_v2.ino` (I2C 수신, `d` = 서보 힘 풀기, USB 115200) |
| 보드 코드 | `board_app/uart.c`, `uart.h` 수정본 (I2C 송신), `run_i2c.sh` |
| 보드 접속 | 랜선 + ssh (`10.42.0.x`, 계정 topst/topst) |
| USB-TTL | **TX → 보드 디버그 RX, GND만 연결.** 콘솔용이 아니라 부팅 멈춤 방지용(RX를 HIGH로 잡아 줌) |

### 0. 우노 펌웨어 (윈도우에서 다른 펌웨어를 올렸을 때만)
- 우노를 보드와 분리하고 노트북 USB에만 연결함.
```
ls /dev/ttyUSB*
sudo pkill picocom; export PATH=$PATH:$HOME/.local/bin && sudo chmod 666 /dev/ttyUSB0 && arduino-cli compile --fqbn arduino:avr:uno ~/model_control_i2c_v2 && arduino-cli upload -p /dev/ttyUSB0 --fqbn arduino:avr:uno ~/model_control_i2c_v2 && echo "업로드 성공"
```
- 포트 이름이 다르면 바꿔서 실행함. USB-TTL이 먼저 꽂혀 있으면 우노는 보통 `ttyUSB1`.
- 업로드가 끝나면 우노 USB를 뺌.

### 1. 보드 부팅
1. 보드 전원을 끈 상태에서 연결함.
   - 노트북 ↔ 보드: 랜선
   - USB-TTL TX → 보드 디버그 RX, GND → GND, USB-TTL은 노트북에 연결
   - **우노는 연결하지 않음**
2. 보드 전원을 넣고 2분 기다림.
3. IP를 찾고 접속함.
```
sudo nmap -sn 10.42.0.0/24
ssh topst@10.42.0.<IP>
```

### 2. 우노 연결 (보드 부팅 후에만)
1. **사격 모터 배터리를 분리함**(사격 시험 전까지).
2. 배선함: 40핀 3 → A4, 5 → A5, 9 → GND.
3. 우노 전원은 **둘 중 하나만** 연결함.
   - 노트북 USB: 로그 확인 가능 → `sudo picocom -b 115200 /dev/ttyUSB1`
   - 40핀 4번(5V) → 우노 5V: 노트북 없이 단독 동작
4. 서보 LiPo를 켬.

### 3. 실행
**보드 ssh 창**
```
cd ~/vulcan_aig_bundle_1124_2 && bash run_i2c.sh
```
- 시작 로그에 `[uart] I2C 연결됨 (/dev/i2c-1, 0x08)`이 떠야 함.
- 실행 중 입력하는 명령
  - `shot`: 1번째 = 선도각 장입, 2번째 = 사격
  - `cancel`: 사격 취소
  - `r`: 중앙 복귀
  - `q`: 종료
- 자주 쓰는 옵션
  - `--pan-sign -1` / `--tilt-sign -1`: 방향이 반대일 때
  - `--conf 0.35`: 탐지 문턱 (기본 0.3)
  - `--jump-reject-frames 3`: 점프 필터 대기 시간 단축 (기본 10)
- 카메라가 3초 끊기면(exit 3) 자동으로 다시 시작함(최대 5회).

**노트북 새 터미널 (추적 화면)**
```
~/venvs/aig/bin/python ~/Downloads/vulcan_aig_bundle_1124_2/vulcan_aig_bundle/pc_viewer/view_aig.py --board 10.42.0.<IP> --port 5001
```
- 초록 박스 = 추적 중인 표적. 화면 위쪽에 pan/tilt 각도와 사격 상태가 나옴.
- 창에서 `q`를 누르면 닫힘(보드 추적은 계속됨).

### 4. 종료
1. 보드 창에서 `q` (또는 Ctrl+C) → 우노에 사격 정지(`x`) + 서보 힘 풀기(`d`)가 자동으로 전송됨.
2. 화면 창 `q`, picocom은 Ctrl+A → Ctrl+X.
3. 서보 LiPo 끄기 → **우노 전원 분리**(USB 또는 4번 선) → USB-TTL 분리.
4. `sudo shutdown -h now` → 20초 뒤 보드 어댑터 분리.

### 안 될 때
| 증상 | 조치 |
|---|---|
| nmap에 보드가 안 잡힘 | USB-TTL(TX→RX, GND)을 연결한 상태에서 보드 전원을 **껐다 켬** |
| `[i2c] 쓰기 실패` | 우노 전원, 3/5/9번 배선 확인. 보드에서 `sudo i2cdetect -y 1` → `08`이 보여야 함 |
| 카메라 끊김 반복 | CSI 케이블 고정·여유 확인, 발열 확인 |
| `CameraSetConfig 실패` | 이전 실행이 남아 있음 → `sudo pkill -9 aig_turret` |
| 강제 종료 후 서보에 힘이 남아 있음 | `sudo i2ctransfer -y 1 w2@0x08 0x64 0x0a` |

### 규칙
- 우노는 **보드 부팅 후에만** 켜고, 끌 때는 **우노를 먼저** 끔.
- 우노 USB와 40핀 4번 5V를 동시에 연결하지 않음.
- 보드 디버그 헤더 TX는 고장 → 쓰지 않음(USB-TTL 콘솔 출력도 안 됨).
